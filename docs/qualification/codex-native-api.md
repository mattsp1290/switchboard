# Native Codex app-server qualification

The pinned Codex 0.169.0 binary passes isolated Linux arm64 and Linux x64 qualification against a synthetic loopback Responses server. The x64 run uses Docker's QEMU emulation on the arm64 host; native x64 CI remains a separate execution environment. This evidence covers the native app-server protocol and its generated public bindings. Real provider access, LiteLLM compatibility, and production authorization remain unqualified.

The reproducible entry point is `spikes/codex-native/qualify.mjs`. It takes an official optional-platform npm archive and an architecture. `pins.json` records the exact arm64 and x64 artifact URLs and SHA512 digests from npm metadata. The Node image is pinned by its OCI index digest. Docker selects the corresponding platform with `--platform`. The runner verifies archive integrity before extracting or executing the binary and asserts its reported version.

The following commands describe the Linux x64 CI invocation with Node 24.22.3 and npm 11.19.1 already selected. The root lockfile provides TypeScript 7.0.2 and Node declarations 24.19.2. The runner verifies those installed versions.

```sh
npm ci --ignore-scripts
mkdir -p spikes/codex-native/.work
curl --fail --location --max-time 120 \
  --output spikes/codex-native/.work/codex-linux-x64.tgz \
  https://registry.npmjs.org/@openai/codex/-/codex-0.169.0-linux-x64.tgz
docker pull --platform linux/amd64 node@sha256:dc26ae92c9fb15cf6b1d63e20f0944b2efe0f115b20e00be48fb23fceb061c54
node spikes/codex-native/qualify.mjs spikes/codex-native/.work/codex-linux-x64.tgz x64
```

The arm64 invocation substitutes `linux-arm64.tgz`, `linux/arm64`, and `arm64`. The runner prints assertion results and observed HTTP calls as JSON. A failed assertion exits nonzero. Generated files and extracted executables live in a unique ignored directory. The runner removes it after confirmed container absence and retains it with its exact path when cleanup remains uncertain.

After binding parity, strict generated-consumer compilation, and the probe, the qualifier compiles the current project into its owned work directory. It requires identical wire source hashes before and after compilation and records both source hashes and the compiled codec SHA-256. Discovery mounts that fresh private codec at `/dist/adapters/codex/wire.js` and the repository ESM manifest at `/dist/package.json`, both read-only. Qualification does not use shared `dist` output.

Each native execution uses `--rm --network none --read-only --pids-limit 128 --cpus 2 --memory 768m`. Fresh tmpfs mounts provide 128 MiB at `/tmp` and 64 MiB at `/root`. Only the verified executable, fixture code including the compiled private wire codec, the repository ESM manifest, and synthetic data are mounted read-only. There are no host credentials, history, home directories, or sockets in the container. There are no `HOME` or `CODEX_HOME` overrides. Synthetic credential commands and native thread state exist only inside the disposable container. Native commands have a 40-second container deadline and a 45-second host deadline. Individual protocol waits have six-second deadlines. HTTP bodies, HTTP request counts, native stdout, host stdout, and archive size have explicit limits.

| Assertion | Observed native behavior |
| --- | --- |
| Initialization | The public `initialize` request succeeds before `initialized` and thread operations. |
| Start-only thread | `thread/start` returns an ID, but another process cannot discover or resume it before its first turn. |
| External discovery | One app-server creates and persists a thread. Another app-server discovers its native ID with `thread/list`. |
| Resume | `thread/resume` returns the same ID and saved turns without an inference request. A subsequent native turn appends while preserving the saved file's byte prefix. |
| Command approval | An advertised `exec_command` call produces a native approval request. The client declines it, the native item becomes `declined`, and the command's marker file never exists. |
| Cancellation | `turn/interrupt` ends a held accepted response with native status `interrupted` after one inference request. |
| Accepted stream failure | A 200 SSE response sends a text delta and ends before `response.completed`. The turn fails after one inference request. |
| Accepted process loss | The app-server is killed after an accepted request. Another process resumes the thread without resubmitting inference or rewriting its saved prefix. |
| Credential cache | Two turns reuse one bearer without another helper invocation. |
| Rejected bearer | One 401 causes exactly one helper renewal and one successful authenticated retry, even when request and stream retry limits are zero. |
| Credential expiry | With a 50 ms refresh interval, a later turn receives a different bearer after the interval passes. |
| Failed proactive renewal | The helper exits nonzero, but Codex sends its cached bearer. The fixture accepts that still-valid token. |
| Failed renewal after 401 | The helper exits nonzero. The native turn fails after one rejected request and makes no accepted retry. |
| Initial credential failure | A new process with a failing helper sends a request without Authorization. The fixture rejects it with 401 and the turn fails. |

The retry assertions set both `request_max_retries` and `stream_max_retries` to zero. They do not establish default retry behavior. Metadata GET requests to `/v1/models` receive 404 and can repeat independently. The report counts those separately from inference POST requests. The extra request after an approval decision is the model continuation, whereas the request after 401 follows rejected authentication. Neither is evidence that accepted work was retried.

The native credential command is not a fail-closed authorization boundary in this configuration. Host invocation denial must prevent invocation. A host requiring zero dispatch after any later native helper failure has a conditional policy conflict unless an additional enforcement path is separately qualified. Preflight alone does not control a later internal refresh. The fixture proves neither token revocation nor upstream OAuth refresh. `refresh_interval_ms` measures cache age; it does not parse token expiry claims. Synthetic tokens contain no account data.

The generated binding check invokes the exact binary's public `app-server generate-ts` command without experimental bindings. Historical qualification produced 784 TypeScript files with extensionless relative module specifiers. The shared transform in `spikes/codex-native/protocol-bindings.mjs` adds `.js` for existing sibling modules and `/index.js` for existing directory modules. It accepts named type imports, type namespace imports, and named or star re-exports with optional `type` and star namespace aliases. Other import dialects fail closed with a bounded statement excerpt. Targets must exist, and source and consumed tree hashes are recorded. Only module specifiers change. Fresh native CI must establish the pinned generator's actual syntax, selected-leaf byte parity, and strict compilation at this head.

All generated files and `consumer.ts` pass TypeScript 7.0.2 with `strict`, NodeNext modules and resolution, `exactOptionalPropertyTypes`, `noUncheckedIndexedAccess`, `verbatimModuleSyntax`, `lib: ["ES2022"]`, Node declarations, and `skipLibCheck: false`. No DOM library, ambient shim, SDK dependency, or global compiler-policy change is needed. This proves the generated-binding approach after the explicit import transform. It does not claim the raw generator output is directly NodeNext-compatible.

Broader adapter qualification still requires live direct and both LiteLLM journeys, approval acceptance and file-change approval journeys, permission and user-question round trips, and explicit outcome-unknown handling after ambiguous process loss. Strict fail-closed behavior after native helper failure is required only when the host selects that stronger policy. Tool execution acceptance remains untested because this fixture only declines the native command request. The host still owns durable admission, writer exclusivity, and the decision to reconcile an uncertain accepted effect instead of retrying it.

Official documentation corroborates the public generator, request lifecycle, and command approval protocol in [Codex app-server](https://learn.chatgpt.com/docs/app-server). The [configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference) documents command credentials, the refresh interval, and its zero-value semantics. The executable assertions establish the exact pinned behavior described above. Documentation was read on 2026-11-13; current documentation is not an immutable substitute for the pinned run.

## Proxy-routed requester

Observed locally with 0.169.0 on macOS against a loopback Responses fixture, not in the qualifier or CI. A custom provider `model_providers.litellm` with `base_url` on the fixture's `/v1`, `wire_api = "responses"` and an `auth.command` helper produced these facts:

- `account/read` returns `{account: null, userId: null, requiresOpenaiAuth: false, workspaceRouting: null}`, with `refreshToken` false or true, before and after a resume in a new process. Turns complete with the helper's bearer.
- `config/read {includeLayers: false}` reports `model_provider: "litellm"` and the full `model_providers.litellm` entry: `base_url` verbatim, `wire_api`, `auth {command, args, timeout_ms, refresh_interval_ms, cwd}`, `requires_openai_auth: false`, and null `env_key` and `experimental_bearer_token`. Built-in providers such as `ollama` are absent from `model_providers` and also report `{account: null, requiresOpenaiAuth: false}`; overriding one is a startup error.
- Combining `requires_openai_auth = true` with provider `auth` is a startup error: `provider auth cannot be combined with requires_openai_auth`.
- A stored `apiKey` login (`account/login/start`) leaves `account/read` unchanged and is not used for requests of threads on the configured provider; the helper's bearer still is.
- Per-thread overrides leave that provider while the login and `config/read` stay unchanged: `thread/start {modelProvider: "openai"}` ran its turn on `openai_base_url` with the stored native API key, `thread/start {config: {model_provider: "other"}}` switched the thread's provider, and `thread/start {config: {"model_providers.litellm.base_url": ".../evil/v1"}}` kept `modelProvider: "litellm"` but sent traffic to `/evil/v1`. `Thread.modelProvider` in start, resume and `thread/read` replies names the thread's provider.
- Without `auth.command`, `requires_openai_auth = true` plus an `apiKey` login projects `{account: {type: "apiKey"}, requiresOpenaiAuth: true}` and does not renew after a 401.

The direct requester therefore cannot bind a command-auth routed app-server. `src/adapters/codex/sessions.ts` binds it, when the host supplies a validated `CodexProxyRoute`, to the host-asserted route principal (boundaries.md, Private Codex sessions). An adapter-level check then ran `openCodexExecution` with that route against the same kind of fixture: routed `create` bound `litellm-proxy:sha256:<hex>` and its turn completed, a direct-mode open of the same home refused `create` and the routed resume as `inaccessible`, and a routed resume in a new process returned the same thread and its turn completed. After the override evidence the check also showed a routed `create` with `modelProvider: "openai"` refused as `invalid-input` before sending and a provider entry with another `base_url` refused as `inaccessible`. The probes ran outside the repository from a session scratchpad (`me4l-probe/probe.mjs` with `run2-out.json`, `ai7m-review/probe.mjs` and `probe2.mjs` with `out.json` and `out2.json`, and `ai7m-native/check.mjs`); they are evidence for this decision, not a reproducible qualifier, and they do not cover a live LiteLLM proxy.

A later probe (`ai7m-confirm/probe7.mjs`, `out7.json`) opened a home holding a routed thread with a direct app-server (`model_provider = "openai"`, the litellm entry still configured, an `apiKey` login). The direct requester bound `apiKey`, `thread/read` reported `modelProvider: "litellm"`, and `thread/resume` succeeded and ran its turn on the proxy `/v1/responses` with the helper's bearer: native resumes a thread on its own provider. With `model_provider` absent (`probe6.mjs`, `out6.json`) `config/read` reports no `model_provider` and native's default is `openai`. Sessions therefore compare every thread's `modelProvider` with the effective provider in both modes (boundaries.md, Private Codex sessions); `ai7m-confirm/check3.mjs` reran the scenario through the adapter (Verification in PR #65).

## LiteLLM route

`src/adapters/codex/proxy.ts` generates the routed app-server configuration and serves its credentials. Evidence is synthetic loopback only; live LiteLLM qualification is owned by switchboard-ov4y.

- The route carries the host-selected LiteLLM model (`route.model`, verbatim, at most 256 characters, no control characters). It is not part of the route principal, so one principal serves sessions on different models and ai7m principals are unchanged; each app-server enforces its own route model (below).
- `codexProxyConfig(route, {auth?: {model?, headers?}, helper, timeoutMs?, refreshIntervalMs?})` returns frozen `-c` overrides and their args for `codex app-server`: `model_provider = <providerId>`, `model = route.model`, and `model_providers.<providerId>` with `name = "LiteLLM"`, `base_url = route.endpoint` verbatim, `wire_api = "responses"`, `supports_websockets = false`, `request_max_retries = 0`, `stream_max_retries = 0`, `requires_openai_auth = false` and `auth {command, args, timeout_ms (1-10000, default 5000; capped at the broker's 10 s per-connection limit), refresh_interval_ms (default 300000)}`, plus `features.multi_agent = false` and `features.multi_agent_v2 = false` (multi-agent restriction below). It never sets `env_key`, a bearer token, ChatGPT or forced-login settings, or `openai_base_url`; this is exactly the entry `routedProvider` admits (sessions.ts), pinned by a round-trip test. Non-empty `AuthRoute.headers` are refused: no native Codex provider header key is qualified. An `auth.model` other than `route.model` is refused.
- Model enforcement (execution.ts): under a route, `model` on `thread/start`, `thread/resume` or `turn/start` unless it strictly equals `route.model`, `collaborationMode` unless it is a `turn/start` object whose `settings.model` strictly equals it (it takes precedence over `model`), and `allowProviderModelFallback` other than `false` (it can replace the requested model) are `invalid-input`, unsent; typed features are merged first. A start or resume reply whose `model` is not `route.model` is `native-failure`, never a session: natively a resumed thread keeps its persisted model over the configured one, so a thread started on another route model resumes only with `model: route.model` passed; the error carries a `message` saying so. The 0.169.0 request bindings have no other model field on these requests, and Switchboard sends no `thread/settings/update` or `thread/fork`. One more model path exists inside a turn: the model's own `spawn_agent` tool call takes a `model` argument, and the sub-agent's requests go out on that model (multi-agent restriction below). Direct mode passes all of these through.
- Multi-agent restriction: the routed config disables native multi-agent, and `codexFeatureCapabilities['multi-agent-under-route']` is `unavailable` with that reason. This is an explicit route restriction, not a silent disable. With 0.169.0 defaults (`codex features list`: `multi_agent` deprecated, on; `multi_agent_v2` stable, off) a routed request offers the `multi_agent_v1` namespace, whose `spawn_agent` takes `model`. `multi_agent_v2` replaces it with the `collaboration` namespace, whose `spawn_agent` also takes `model`. `-c` outranks a home or project `config.toml`, and routed thread `config` is refused, so the host cannot re-enable either. The routed bind also verifies the pins: `routedProvider` requires `config/read` to report `config.features.multi_agent` and `config.features.multi_agent_v2` as `false` (0.169.0 reports `-c features.x=false` nested under `features` and omits an unset feature), so a host that spawned codex without the generated args gets `inaccessible`. No other tool in the routed request carries a model or provider argument (`exec_command`, `write_stdin`, `request_user_input`, `view_image`, the goal tools, `web_search`). The guardian approval reviewer (`approvalsReviewer: "auto_review"`, `guardian_approval` on by default) sent its assessment on the route model, even when `/v1/models` also listed `codex-auto-review` and `gpt-5.6-luna`, so it stays enabled.
- `startCodexCredentialBroker(scopedAuth, {invocationId, route, signal})` takes its endpoint and model from the route, so it cannot diverge from `codexProxyConfig`. It listens on a unix socket in a fresh 0700 temp directory. Its helper is `process.execPath proxy-helper.js <socket>`: no token in argv, the environment or a file. Each helper connection (an empty half-close) is one native request boundary: `resolve({boundary: 'request', invocationId, requestId: randomUUID()})`, never cached. A failed, aborted, header-carrying, non-LiteLLM or oversized resolution, one whose endpoint or model differs from the route, one that is not `protocol: 'responses'` with `credentialPurpose` and `material.purpose` `litellm-proxy`, or a token that is not printable ASCII (0x21-0x7E) writes nothing. Native trims the helper's stdout, and a newline inside a token makes native send no Authorization at all, so the broker never relies on either; the helper then prints the fixed stderr `switchboard: proxy credential unavailable` and exits 3. At most 4 concurrent connections, 64 KiB of token and 10 s per connection; a connection that sends any byte is dropped. `close()` (or the signal) removes the socket and directory. Use one broker per app-server; brokers share nothing. Same-user processes can reach the 0700 directory: they can ask it for tokens, and by holding all 4 connections they make the helper fail at once until the idle ones are dropped after 10 s. A socket path beyond the platform limit (a long `TMPDIR`) fails as `credential-unavailable` and leaves no directory.
- Native calls the helper on the first request of a process, after `refresh_interval_ms`, and once after a 401. The token is cached in between, so rotation takes effect at those points, not per HTTP request.
- Restriction: when the helper fails on a process's first request, native still dispatches that request to `base_url` without Authorization; the proxy answers 401, renewal fails and the turn fails. There is no direct fallback because `base_url` is the proxy and no other credential is configured. Native's failure message embeds the helper's stderr, which is why it is fixed text.
- Subscription passthrough is absent: provider command auth reports `{account: null, requiresOpenaiAuth: false}`, so the generated configuration cannot bind or run as a ChatGPT or stored API-key requester in direct mode, and a routed bind refuses any native login. Direct native mode is unchanged and does not use this module.

Native check (`me4l-native/check.mjs` and `out.json`, session scratchpad, local macOS 0.169.0, loopback fake `/v1`): through `openCodexExecution` with the route, codex spawned with `codexProxyConfig` args and the real broker. A routed create bound `litellm-proxy:sha256:...` on provider `litellm` with model `team/rot-model`; turn 1 sent `rot-1` (200); after the host revoked every token, turn 2 sent `rot-1` (401), the helper resolved `rot-2` and the retried request passed; a resume in a new process resolved `rot-3` and its turn passed; resolutions used distinct request ids and argv held no token. A broker whose resolver throws produced one `/v1/responses` without Authorization (401) and a failed turn. Two brokers driving two app-servers in parallel each sent only their own tokens and models. The ChatGPT and `openai_base_url` sentinel received nothing; besides `/v1/responses`, native only sent `GET /v1/models` to the proxy. The review rerun (`me4l-native2/check.mjs`) repeated all of this and added the model checks: `thread/start` and `turn/start` with `model: "gpt-5.1-codex"`, and a `collaborationMode` on it, were refused `invalid-input` with no proxy request; a turn passing the route model sent `team/rot-model`. The same thread resumed by an app-server on route model `team/rot2-model` was reported on `team/rot-model` and refused `native-failure`; resumed with `model: "team/rot2-model"`, its turn sent `team/rot2-model`. The multi-agent round (`me4l-c4/probe7.mjs` with `head-default.json`, `head-hometoml.json`, `new-spawn.json`, `new-hometoml.json`, `guardian-new.json` and `native2-out.json`) had the fake `/v1` answer a `spawn_agent` call naming another model. Before the restriction, `multi_agent_v1.spawn_agent` with `model: "gpt-5.5"` produced a `/v1/responses` on `gpt-5.5` with the route token. A home `config.toml` enabling `multi_agent_v2` did the same through `collaboration.spawn_agent`. With the restriction, neither namespace was offered, either call returned `unsupported call`, and every request used `team/rot-model`, including with that `config.toml` present. Rerunning `me4l-native2/check.mjs` gave the same results as before, and the cross-model resume `native-failure` now carried its message. The pin round (`me4l-pin/probe.mjs` and `out.json`) read `config/read` on scratch homes: with the pins `config.features` held `multi_agent: false` and `multi_agent_v2: false`; without them both keys were absent; a home `config.toml` enabling both, overridden by the pins, read `false`, and without the pins read `true`. A rerun of `me4l-native2/check.mjs` repeated every routed flow unchanged and, spawned without the two pins, a routed create was `inaccessible` with no proxy request or broker resolution.

## Native feature settings

`src/adapters/codex/features.ts` validates typed host settings against the 0.169.0 bindings and these native rules, observed with 0.169.0 against a real `codex app-server` and a scratch `CODEX_HOME`:

- Experimental fields fail natively with the binary's `<field> requires experimentalApi capability` error unless `initialize.capabilities.experimentalApi` is `true`. Observed: `thread/start.permissions requires experimentalApi capability` and `askForApproval.granular requires experimentalApi capability`. `permissions` appears on `thread/start`, `thread/resume` and `turn/start` only in the `generate-ts --experimental` bindings, and `dynamicTools` only on experimental `thread/start`. With typed features present, the adapter refuses `permissions`, a granular `approvalPolicy` and `thread/start.dynamicTools` before sending when the capability is absent.
- Defaulted fields may be omitted, as in the `generate-json-schema --experimental` required lists: a granular policy without `skill_approval` and `request_permissions` was accepted, and every `SandboxPolicy` field except `type` has a native default.
- Dynamic tool names follow the binary's own error strings: `dynamic tool name must not be empty`, `dynamic tool name has leading/trailing whitespace`, `duplicate dynamic tool name`, `duplicate dynamic tool name in namespace`, `dynamic tool namespace must contain at least one tool` and `deferred dynamic tool must include a namespace`. The adapter checks these on typed `dynamicTools` only. Reserved names and the Responses API name pattern remain native checks.
- The legacy dynamic tool form `{name, description, inputSchema}` without `type` was accepted, so raw `dynamicTools` pass unchanged.
- A relative `cwd` resolved against the app-server's own directory, so typed `cwd` and `writableRoots` must be absolute.

### Using typed features

- Pass `features` on `create`, `resume` or `turn`. Raw `params` keep engine-specific keys unchanged and are never re-validated. A typed field equal to its raw key is accepted. A different one fails as `invalid-input` naming the field ("remove it from raw params or make the values equal"), and nothing is sent. Without `features`, raw params pass exactly as before.
- `null` means unset, as natively: a typed `null` adds nothing, and conflicts with a non-null raw value.
- `codexFeatureCapabilities` labels each feature `qualified`, `fixture-only`, `typed-unqualified` or `passthrough-unqualified` with its carriers per request, marks dynamic tools after start `unsupported`, marks routing `fixture-only` and multi-agent under a route `unavailable` (LiteLLM route below).
- `permissions`, a granular `approvalPolicy` and `dynamicTools` need `experimentalApi: true` in the connection's `initialize`, read once when the connection opens.
- Dynamic tools are fixed at `thread/start`: neither `thread/resume` nor `turn/start` can add or change them.
