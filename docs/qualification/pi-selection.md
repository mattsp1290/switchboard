# Pi selection evidence

Observed on 2026-11-13 for switchboard-rlsx. Prefer a thin adapter over the public Pi coding-agent SDK and its `ModelRuntime`. This preserves native session identity, resources, extensions, and events without implementing another agent loop. Selection is provisional. The exact SDK fails Switchboard's current declaration gate, and the required extension/proxy policy combination still needs an enforcing design and qualification. Neither finding proves that the native runtime lacks the required capability.

## Reproduce the bounded evidence

Run the following on macOS with Node 24.22.3 and an absolute path to the npm 11.19.1 CLI script. The runner requires `/usr/bin/sandbox-exec` and a temporary directory outside the production home.

```sh
node spikes/pi/run.mjs /absolute/path/to/npm/bin/npm-cli.js
```

The runner creates a private temporary consumer, copies the exact lockfile, and runs `npm ci --ignore-scripts`. Every dependency has a registry URL and SHA512 integrity. No global installs or lifecycle scripts run. The child environment has a bounded system PATH, explicit temporary npm configuration, `PI_OFFLINE`, and `PI_CODING_AGENT_DIR`. `TMPDIR` is inside the consumer. `HOME` is omitted and never reassigned. Only npm version checking and dependency installation run outside the fixture restrictions; installation uses the registry network.

SDK fixtures run with Node filesystem permissions and an inherited macOS sandbox. Node permits reads and writes within the consumer. Its one additional read permission lets Pi check the native `~/.agents/skills` path, which the OS sandbox denies before discovery. The sandbox denies production-home reads and existence checks except for the pinned Node executable, denies all network operations, and permits writes only within the consumer and to `/dev/null`. Execution is limited to Node, fixed system `sh`, its macOS `bash` variant, `cat`, and the pinned native TypeScript compiler. A preflight checks denied outside-consumer Node reads and writes, denied sentinel reads and existence checks, denial inherited by `cat`, and a denied loopback listen before SDK imports. The loader fixture has a synthetic `.git` boundary, disabled context discovery, and an empty explicit system prompt. These restrictions protect this trusted fixture run; arbitrary extension isolation is not qualified. This runner has no Linux or Windows isolation implementation.

Fixture credentials are explicit strings or temporary files. Offline settings also suppress model refresh, but network denial comes from the OS sandbox. Every runner subprocess has a 60-second timeout. The runner retains isolation and fixture logs and `result.json` in the printed directory. It exits nonzero when the real declaration gate fails, even when fixtures pass.

The compiler is TypeScript 7.0.2 with `@types/node` 24.19.2, strict NodeNext, ES2022 only, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, and `skipLibCheck:false`. No ambient shims, declaration patches, DOM library, or ignored diagnostics are supplied.

The recorded [result](../../spikes/pi/results.json) has six passing fixture tests and a nonzero declaration gate. They use native public SDK methods with synthetic data and explicitly supplied temporary roots. No CLI session, native turn, provider request, model call, production history access, or live credential resolution occurred. These are SDK behavior probes, not live backend qualification.

## Crew's boundary is useful evidence, not a default policy

At [PR 61's exact head](https://github.com/mattsp1290/crew/blob/7bedb00bc2a631b16c25d86d1a4ff5dff199714b/src/service/pi-launch.ts), `providerHooks` runs `profile.prepare` on the host. Its extension proxy accepts only `on`, restricted to `before_provider_headers`, `before_provider_request`, `after_provider_response`, and `provider_stream_event`. Any other API or context access throws. The host forwards those hooks into `transformHeaders`, `onPayload`, `onResponse`, and `onProviderStreamEvent`, fixes retries to zero, and calls `verify` after successful work. Prepared hooks are cached per worker invocation, so credential renewal must occur inside each request hook or provider auth resolution, not only inside `prepare`.

Crew's worker does not receive the profile closures. Its host owns provider streaming, tools, request bounds, and confined process execution. The source also disables ordinary resource discovery, restricts tool catalogs, reconstructs in-memory checkpoints, and uses application-specific result checks. Copying that confinement or checkpoint policy would discard required native behavior in a reusable library. Preserve configurable host preparation and enforcement seams while retaining Pi's native extension model for hosts that permit it. Crew's tests are not evidence for live Pi, LiteLLM, or other host platforms.

## Reuse comparison

`@ai-sdk/harness-pi` preserves substantial native functionality, including extension factories, credential stores, native journal entries, and optional session storage. Its `src/pi-session.ts` creates `SessionManager.inMemory` from supplied storage and owns parked sessions. External native-file discovery would still need a separate bridge. Its `src/pi-auth.ts` accesses private `ModelRuntime.models.authContext` to scope environment authentication and mutates provider auth objects. Those private assumptions, plus sandbox/session lifecycle policy, make it a poor foundation for the requested public-API boundary. Reusing specific ideas is preferable to depending on the whole adapter. No claim of complete native feature loss is made.

`pi-acp` lists native history, resumes through Pi RPC, exposes extension UI requests, and advertises load-session support. Its implementation parses session files itself rather than using `SessionManager.list`, launches a separately selected Pi CLI, and `loadSession` calls `closeAllExcept`. Its RPC boundary does not expose an in-process host `CredentialStore` or `ModelRuntime` injection seam. Additional extensions or protocol work would be needed to preserve the required credential and concurrent-session semantics. [Zed's Pi page](https://zed.dev/acp/agent/pi) confirms the bridge packaging and `pi-acp@0.0.34` launch entry. Prefer direct public SDK composition for this task.

## Declaration blocker and remaining decisions

The full public API import produces 48 diagnostics, recorded in [`declaration-errors.txt`](../../spikes/pi/declaration-errors.txt). There are 43 TS1543 errors for JSON model declarations without NodeNext import attributes. The pinned `@google/genai` 2.21.0 dependency adds five errors involving missing MCP SDK declarations and Node-only `RequestInfo`, `ErrorEvent`, and `HeadersInit`. JavaScript public-root import succeeds. This is an observed declaration compatibility failure, not evidence of runtime impossibility.

The coding-agent export map exposes only the root and an executable `rpc-entry`, with no typed SDK subpath. A separate public `@earendil-works/pi-ai/models` import still fails on the five Google declarations and does not provide native sessions or extensions. The runner reproduces that alternative too. No private-file import bypass was adopted. Resolution requires an upstream declaration fix or an explicitly reviewed compilation boundary compatible with Switchboard's public contract. This spike does not weaken the repository gate.

The required combined extension/proxy policy remains unresolved until enforcement survives endpoint replacement, custom `streamSimple`, native provider registration, payload hooks, auth failure, and hooks that throw. Inspection at startup alone is insufficient for extensions that re-register providers later. Public `ExtensionRunner.bindCore` provides provider action hooks, but the complete session lifecycle and final transport boundary were not exercised. The adapter must preserve allowed extensions and report incompatible customizations instead of silently suppressing extensions.

These are blockers to implementation acceptance under the current choices. Later live qualification separately requires direct and LiteLLM turns, CLI-created external sessions, actual provider/proxy/model versions, renewable credentials during multi-request and resumed sessions, tools and approvals, cancellation, concurrency, bounded observers, and uncertain outcomes. Missing live runs are a pending evidence requirement, not a conclusion that integration is impossible. No required combination is dropped.
